## 3. 리드가 지목한 세 가지

### (a) 파생 shard의 basename이 충돌하고, 이름 규약이 계획에 없다 — 실행 블로커

`:622`는 "`run_mimic_image_batch.py`와 `rerender_initial_frames.py`도 수정이 필요 없다"고 적고,
`:634`는 "합치기 전 76개분 provenance 해시를 대조해 설정 동일성을 확인한다"고 적는다.
**"합치기"를 수행할 수단이 없다.**

**충돌은 실재한다.** 76개 파생 세트와 112개 신규 세트가 **같은 원본 20샤드 전부**에서 나온다.

```
76개가 쓰는 샤드 20, 112개가 쓰는 샤드 20, 교집합 20
```

그리고 `rerender_initial_frames.py:113`이 출력 이름을 원본과 같게 고정한다.

```python
113:  dst_path = output / raw_path.name        # shard_000.hdf5 … shard_019.hdf5
176:  provenance["shards"].append({"filename": raw_path.name, ...})
```

따라서 두 세트 모두 `shard_000.hdf5` … `shard_019.hdf5`를 갖는다. **20건 전면 충돌이다.**

**변환기가 이를 허용하지 않는다.** `run_mimic_image_batch.py`의 제약 넷이 동시에 걸린다.

```
138-139:  if not isinstance(filename, str) or Path(filename).name != filename:
              raise ValueError("selection shard filename must be a basename")   # 하위 경로 불가
142:      raw = (raw_dir / filename).resolve(strict=True)                        # 단일 raw_dir
143-144:  if item.get("raw_sha256") != sha256(raw): raise ...                    # 결정적 제약
257-258:  if selection_manifest is not None and raw_dir is None: raise ...
```

`:143-144`가 결정적이다. 매니페스트의 `raw_sha256`은 **`raw_dir/filename`에 있는 그 파일의 해시**여야 한다.
서로 다른 두 `shard_000.hdf5`는 해시가 다르므로 한 디렉터리에 공존할 수 없고,
하나의 매니페스트가 둘을 동시에 가리킬 수 없다.

**우회할 수 없다.** 각 arm이 두 세트를 반드시 섞는다.
기존 6계열 풀 112개 = 재렌더된 76개 + 신규 36개이고, 새 3계열 76개는 전부 신규다.
S-arm(6계열)조차 76 + 36을 섞어야 하므로, 어떤 arm도 한 세트만으로 구성되지 않는다.

**감사도 같은 이름으로 충돌한다.** 기존 76개 세트의 실제 구성을 확인했다.

| 항목 | 값 |
| --- | --- |
| `mimic_reset_fixed_76_20260921/plan.json`의 `raw_dir` | `outputs/mimic_reset_fixed_76_20260921/raw` |
| `selection_manifest` | `outputs/evaluation/mimic_quality_reset_fixed_20260921/candidate_selection.json` |
| `shards[0].filename` | `shard_000.hdf5` |
| `shards[0].raw_sha256` | `4ca800f1…` = **파생** shard 해시 (원본은 `82359e3e…`) |
| `shards[0].audit_path` | `…/mimic_quality_reset_fixed_20260921/audits/shard_000.json` |

`:158-159`가 `audit["input_sha256"] == item["raw_sha256"]`를 단정하므로 **감사는 파생 shard마다 다시 돌려야 하고**,
감사 산출물도 `audits/shard_000.json`처럼 같은 이름을 쓴다. 충돌이 한 겹 더 있다.

`:507`이 근거로 든 "이미 쓰이는 경로"는 사실이지만, 그 선례는 **한 디렉터리에 한 세트**를 둔 경우다.
두 파생 세트를 합친 선례가 아니다.

**해법 셋. (A)를 권한다.**

| 방법 | 내용 | 새 코드 | 추가 비용 | 위험 |
| --- | --- | --- | --- | --- |
| **(A) 188개를 한 번에 재렌더 (권장)** | `:632` 표의 "전량 188개" 행을 채택. 한 디렉터리·한 감사·한 매니페스트 | **없음** | GPU +25분, 디스크 +1.23 GB | 가장 낮다. 이름 규약 자체가 필요 없다 |

(A)의 대가는 `:783`이 지적한 대로 디스크 여유가 2.2 GB에서 약 1.0 GB로 줄어드는 것이다.

### (b) 프레임·밀도·S′ 수치는 비례 기댓값이다 — 일부만 표시돼 있다

**계열 안에서 에피소드 길이가 정확히 상수**임을 확인했다. 9계열 모두 `unique = 1`이다.
따라서 기댓값과 실제 배분의 유일한 차이는 **계열별 에피소드 수의 분수→정수 반올림**뿐이다.

| 항목 | 비례 기댓값 (계획) | 정수 배분 (재계산) | 차 |
| --- | --- | --- | --- |
| N-arm 프레임 | 53,252 | 52,957 | −0.6% |
| S-arm 프레임 | 39,609 | 39,729 | +0.3% |
| close 밴드 비중 N / S | 4.73% / 6.36% | 4.76% / 6.34% | - |
| 80,000 표본 close 노출 N / S | 3,786 / 5,090 | 3,807 / 5,074 | - |
| **S′ 스텝** | **7,438** | **7,502** | **+64 (0.9%)** |

정수 배분 내역은 이렇다.

```

S-arm: demo_7 24, demo_5 23, demo_4 16, demo_9 8, demo_8 8, demo_1 5
```

**표시 상태가 갈린다.**

- `:973`은 프레임 53,252 / 39,609를 **"비례 층화 가정에 따른 계산"**으로 추정 목록에 넣었다. 정확하다.
- 그런데 `:553-580`의 공변량 표는 그 기댓값에서 파생된 4.73% / 6.36%, 3,786 / 5,090, 1.50 / 2.02를
  **확정값처럼 싣고**, `:558`이 이 표를 근거 JSON의 **필수 항목**으로 지정한다.
  사전 등록해 기록할 공변량은 기댓값이 아니라 **실현값**이어야 한다.
- `:574`의 **`--steps 7438`은 리터럴 CLI 인자다.** S′의 존재 이유가 노출을 정확히 맞추는 것인데,
  실현 배분에서는 7,502가 맞다. 7,438을 쓰면 노출이 N보다 약 0.9% 낮게 어긋난다.
  차이가 작아 결론을 바꾸지는 않지만, **정확 정합을 목적으로 하는 arm에 근사값을 박아 두는 것은 설계와 어긋난다.**

`run_act_vision_experiment.py:131`의 `--save_freq={min(5000, steps)}`와 `:258`의
`f"{args.steps:06d}"` 체크포인트 경로를 확인했다. 7,438이든 7,502든 코드 변경 없이 동작한다.
`:575`의 주장은 맞다.

**고칠 것은 값이 아니라 산출 시점이다.** S′ 스텝을 실현된 `split_provenance.json`의 프레임 수로

### 원칙 일관성

받쳐 준다. 이번 재계산에서 0.8992가 정확히 재현됐다.

원칙 2(비용 오름차순과 게이트)는 2.4를 실행 안 함으로 유지하고 S′를 모호 분기 한정으로 둔 데서 일관된다.

### 공정한 대안

`:503-509`의 (i)·(ii) 비교표는 비용과 위험을 양쪽 다 적었고 기각 사유가 구체적이다.

다만 그 선택이 **병합 가능성이라는 세 번째 축**을 빠뜨렸다. 그 축을 넣으면 결론이 뒤집힌다.

S′를 "주 판정이 아니라 강건성 보고"로 격하한 `:578`의 판단은 타당하다.
어느 정합도 완전하지 않다는 인정이 정확하다.

### 위험 완화

1.1.7이 3차 지적을 전부 받았다. `:390`의 "추종 근거를 창 안의 정당화로 쓰지 않는다",

`:578`의 "S′는 노출을 맞추는 대신 총 경사 스텝을 맞추지 못한다"는 자기 한계 인정도 정확하다.

`:612-616`의 중단 조건 자기비판이 특히 좋다. "이 가드는 통과가 예상되므로 통과를 검증 근거로
오독하지 않는다"는 문장은 사전 등록 가드가 흔히 빠지는 함정을 직접 막는다.

빠진 것은 지적 a의 이름 규약과, 파생 shard마다 감사를 다시 돌려야 한다는 사실(지적 E)이다.

### 검정 가능한 수용 기준

§2.2.4의 해석 비대칭 사전 등록(`:566-571`)이 4판의 핵심 개선이다.
"S가 더 나쁘면 34% 유리한 조건에서도 졌다는 뜻이라 증거가 강화되고,
같거나 더 나으면 모호하다"는 구분은 정확하고, 모호 분기에서만 S′를 붙이는 조건부 설계도 합리적이다.

`:600-604`의 자기비판도 이례적으로 정직하다. 잡음 바닥이 한 번 추출한 확률변수라 분산이 크고
검정의 운영 특성이 좋지 않다는 것, `chunk_close_hit` 차이 0.2가 표준오차의 약 1.0배라는 것을
스스로 적었다. 이 규모에서 무엇을 주장할 수 있는지 과장하지 않는다.

남은 흠은 S′ 스텝의 근사값(지적 b)과 공변량 표의 기댓값 기록(지적 C)이다.

**사소한 정합 확인 하나.** 1.1.5의 "표본 2 에피소드 이하 계열은 계열별 판정에서 제외"를 E에 그대로
적용하면 E_old는 계열당 2개라 계열별 분해가 전부 빠진다. 2.2.5는 E_old를 12개 집계로만 쓰므로
실제 충돌은 없다. 그 사실을 한 줄로 적어 두면 구현자가 헷갈리지 않는다.
