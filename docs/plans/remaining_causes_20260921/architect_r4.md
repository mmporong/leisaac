# Architect 재검토: 남은 원인 3건 조사 계획 revision 4

## 종합 판정

3차 검토의 실행 전 필수 2건과 기록 5건이 **전부 해소**됐습니다. 특히 split 도구 제약을 불변식 완화가 아니라
arm별 108개 파생 데이터셋으로 우회한 판단은 정확합니다. `action_contract.py`의 계약 검증자를 건드리지 않는
쪽을 택한 것은 "게이트를 편의상 완화하지 않는다"는 인계 조건과도 맞습니다.

채택한 변환 경로가 실제로 존재하고 필요한 조건을 강제한다는 것도 코드에서 확인했습니다.
`run_mimic_image_batch.py`의 `load_selection_manifest`가 원시 해시, 감사 해시, 임계 일치, 관절 한계 일치,
그리고 **선택된 demo가 전부 `accepted=True`여야 한다**는 조건까지 검사합니다.
계획이 `audit_mimic_quality.py`에 허용오차 인자를 넣기로 한 것이 이 사슬의 마지막 고리를 채웁니다.

남은 블로커는 하나입니다. 신규 112개만 재렌더해 기존 76개와 합치는 방식이 **샤드 파일명 충돌**을 일으킵니다(F1).
변환 도구가 샤드를 `raw_dir / filename`으로 해석하고 `filename`을 basename으로 강제하므로,
188개가 단일 디렉터리에 고유 이름으로 있어야 합니다. 계획에 이름 충돌 해소 규약이 없습니다.

## 2. 새 방식의 검증 결과

### 2.1 arm별 108개 변환 경로는 실재하고 조건을 강제합니다

계획 513행이 인용한 명령의 구성 요소를 전부 확인했습니다.

| 인용 | 실제 | 판정 |
| --- | --- | --- |
| `--convert-only` | `run_mimic_image_batch.py:206` | 실재 |
| `--selection-manifest` | `:215-217` | 실재 |
| `--total` | `:218`, 기본 500 | 실재 |
| `--selection-manifest requires --raw-dir` | `:257-258` | 실재 |
| 선택 수 == `--total` 단정 | `:266` | 실재 |
| 계획 200행의 `:215`, `:254-258` 인용 | 정확 | 일치 |

`load_selection_manifest`(`:117-179`)가 강제하는 조건입니다. 이것이 "감사 매니페스트·raw sha·audit 일치가
실제로 충족되는가"에 대한 답입니다.

| 줄 | 조건 |
| --- | --- |
| `:138` | `filename`이 basename이어야 한다 (디렉터리 성분 금지) |
| `:139` | `raw = (raw_dir / filename).resolve(strict=True)` |
| `:143` | 매니페스트의 `raw_sha256`가 실제 파일 해시와 같아야 한다 |
| `:145-146` | 샤드별 `audit_path`가 실재하고 `audit_sha256`가 맞아야 한다 |
| `:151-154` | 감사의 `max_action_step_norm`이 변환 임계와 같아야 한다 |
| `:155-156` | 감사의 `joint_limits`가 변환 관절 한계와 같아야 한다 |
| `:157-159` | 감사의 `input_sha256`가 `raw_sha256`와, `action_source`가 변환값과 같아야 한다 |
| `:160-170` | 감사의 `episode_count`·`accepted_count`·`rejected_count` 정합성 |
| `:171-173` | **선택된 demo가 전부 `accepted=True`여야 한다** |
| `:174-176` | `(raw_sha256, name)` 중복 금지 |

기존 매니페스트 스키마도 확인했습니다. `outputs/evaluation/mimic_quality_reset_fixed_20260921/candidate_selection.json`이
샤드 20개 항목을 가지고 각 항목이 `raw_path`, `raw_sha256`, `audit_path`, `audit_sha256`, `selected_demo_names`,
`filename`을 담습니다. 감사는 `audits/shard_XXX.json`으로 **샤드별**입니다.

**따라서 사슬은 이렇게 닫힙니다.** 병합 raw 디렉터리에 `audit_mimic_quality.py --max-clip-correction-rad 0.05`로
샤드별 감사를 다시 돌리면 188개가 `accepted=True`가 되고, 그 감사를 참조하는 arm 매니페스트 3종을 만들면
`:171-173`을 통과합니다. **계획이 `audit_mimic_quality.py`에 허용오차 인자를 넣기로 한 것이 이 조건의 전제입니다.**
이 변경 없이는 신규 112개가 `accepted=False`라 변환이 `:173`에서 죽습니다. 계획의 고칠 파일 표에 이미 있습니다.

### 2.3 S' 7,438스텝 산출은 타당하고 코드 변경 없이 실행됩니다

산술을 재계산했습니다.

| 항목 | 값 |
| --- | --- |
| N의 close 노출 (10,000스텝) | 80,000 × 2,520 / 53,252 = 3,785.77 |
| S at 7,437스텝 | 3,785.25 |
| **S at 7,438스텝** | **3,785.76** |
| S at 7,439스텝 | 3,786.27 |

**7,438이 최적 정수입니다.** 계획 575행이 "3,787로 N의 3,786과 맞는다"고 적었는데 둘 다 3,786입니다.
1단위 반올림 차이라 결론에 영향이 없습니다 (F3에 포함).

실행 가능성도 확인했습니다. 계획은 `--save_freq = min(5000, steps)` 때문에 체크포인트가 나온다고 적었는데
**기제가 다릅니다.** 실제로는 `should_save_checkpoint`가 최종 스텝에서 무조건 저장합니다.

```
$HOME/lerobot/src/lerobot/common/train_utils.py:63
    return (save_freq > 0 and step % save_freq == 0) or step == total_steps
```

그리고 디렉터리 이름이 맞는지도 확인했습니다.

```
$HOME/lerobot/src/lerobot/common/train_utils.py:44-46
    num_digits = max(6, len(str(total_steps)))
    return f"{step:0{num_digits}d}"
```

`total_steps = 7438`이면 `max(6, 4) = 6`이라 `007438`이 되고,
`run_act_vision_experiment.py:258`의 `f"{args.steps:06d}"`와 정확히 일치합니다.
`verify_checkpoint`(`:143`)의 `training_state["step"] != steps` 검사도 통과합니다.
`validate_video`(`:189`)의 `result["steps"]`는 롤아웃 스텝이라 학습 스텝과 결합돼 있지 않습니다.

**결론: S'는 코드 변경 없이 실행됩니다. 근거 문장만 틀렸습니다.**

#### F1 상세

변환 도구가 샤드 파일을 이렇게 찾습니다.

```
scripts/imitation_learning/run_mimic_image_batch.py:138-139
    if not isinstance(filename, str) or Path(filename).name != filename:
        raise ValueError("selection shard filename must be a basename")
    raw = (raw_dir / filename).resolve(strict=True)
```

`filename`은 basename이어야 하고 파일은 `raw_dir` 바로 아래에서 찾습니다.
따라서 **188개 에피소드의 샤드가 단일 디렉터리에 고유 basename으로 있어야 합니다.**

그런데 계획이 채택한 구성은 두 디렉터리를 합치는 것입니다.

- 기존 76개: `outputs/mimic_reset_fixed_76_20260921/raw/shard_000.hdf5` 외 20개
- 신규 112개: `rerender_initial_frames.py`가 원본 20샤드에서 파생해 새 디렉터리에 씁니다

둘 다 원본 `mimic_vision224_500_20260913/raw`의 같은 20샤드에서 나오므로 **basename이 그대로 겹칩니다.**
두 `shard_000.hdf5`는 서로 다른 내용(전자는 기존 76개 중 4개, 후자는 신규 112개 중 해당분)이라
한쪽을 덮어쓰면 에피소드가 사라지고, 덮어쓰지 않으면 한 디렉터리에 담을 수 없습니다.

`:174-176`의 중복 검사는 `(raw_sha256, name)` 쌍을 보므로 내용 해시가 다른 두 파일에 같은 demo 이름이 있어도
잡아내지 못합니다. 두 집합이 구성상 서로소라 실제 중복은 없겠지만, 안전망이 없다는 뜻입니다.

처방은 셋입니다.

1. **신규 112개를 다른 basename으로 씁니다.** 예를 들어 `tol005_shard_000.hdf5`처럼 접두사를 붙이거나
   샤드 인덱스를 20부터 시작합니다. `rerender_initial_frames.py`가 출력 이름을 어떻게 정하는지 확인하고,
   고정돼 있으면 재렌더 뒤 리네임 단계를 명시합니다. 내용 해시는 바뀌지 않습니다.
2. **기존 76개를 병합 디렉터리로 복사하면서 리네임합니다.** 원본 디렉터리를 읽기 전용으로 두라는
   865행의 요구와 양립합니다.
3. **전량 188개를 한 번에 재렌더합니다.** 이름 문제가 사라지지만 87분·4.24 GB이고,
   783행이 이 경우 여유가 1.0 GB로 줄어 자원상 곤란하다고 이미 적고 있습니다.

1번이나 2번을 골라 2.2.7에 한 문단으로 적으십시오. 어느 쪽이든 **감사는 병합 디렉터리에서 다시 돌려야 합니다.**
허용오차 인자 적용 때문에 어차피 필요한 단계이므로 추가 비용은 없습니다.
다만 매니페스트의 `audit_path`가 새 basename에 대응하는 감사 파일을 가리켜야 `:145-146`과 `:157-159`를 통과합니다.

#### F2 상세

계획의 프레임 수는 **비례 기댓값**이고 정수 층화 배분으로는 그 값이 나오지 않습니다.

| 항목 | 계획 (기댓값) | 정수 층화 배분 |
| --- | --- | --- |
| N-arm 학습 프레임 | 53,252 | 52,957 |
| S-arm 학습 프레임 | 39,609 | 39,729 |
| close 밴드 비중 N | 4.73% | 4.759% |
| close 밴드 비중 S | 6.36% | 6.343% |

| S' 정합 스텝 | 7,438 | 약 7,461 |

배분은 최대잉여법(비례 배분 후 소수부 큰 순으로 잔여 할당)으로 계산했습니다.
다른 반올림 규칙을 쓰면 값이 또 달라집니다.

결론에는 영향이 없습니다. 밀도비 1.33과 1.34는 같은 이야기이고 해석 규칙도 그대로입니다.
다만 **공변량 표를 근거 JSON의 필수 항목으로 둔 취지가 실제 노출을 기록하는 것**이므로,
표의 출처를 "계획 시점 기댓값"이 아니라 "구성된 split의 실측"으로 규정하십시오.
S' 스텝도 S split이 확정된 뒤 계산해야 하고, 574행의 `--steps 7438`은 예시로 표시하십시오.

#### F3 상세

575-576행이 이렇습니다.

> `--save_freq = min(5000, steps)`이라 코드 변경 없이 7,438스텝 체크포인트가 나온다.

`min(5000, 7438) = 5000`이므로 주기 저장만으로는 5,000스텝 체크포인트만 나옵니다.
7,438이 나오는 진짜 이유는 `should_save_checkpoint`가 `step == total_steps`에서 무조건 저장하기 때문입니다
(`train_utils.py:63`). 결론은 맞고 실행도 됩니다. 근거만 바꾸십시오.
그리고 575행의 "3,787"은 3,786입니다.

#### F4 상세

577-578행이 "S'는 노출을 맞추는 대신 총 경사 스텝을 맞추지 못한다"고 적은 것은 정확합니다.
그 귀결을 한 줄 더 적으십시오. S'는 10,000이 아니라 7,438스텝이므로 **close 밴드만이 아니라 전 구간에서
26% 적게 학습합니다.** 백본과 인코더가 공유되므로 전역적으로 덜 수렴합니다.
따라서 S'가 N보다 나쁘게 나와도 "close 노출을 맞췄는데도 졌다"와 "전역 과소적합"을 가르지 못합니다.
강건성 보고라는 위치 설정은 맞지만, 이 한계를 적어야 결과를 과대 해석하지 않습니다.

#### F6 상세

764행이 2.2 내부 순서를 "재렌더 112개 → 감사 → arm 3종 변환 → split 3종 → 학습 3건"으로 적습니다.
그런데 "감사"가 `audit_mimic_quality.py`를 직접 부르는 것인지 `run_screened_mimic_pipeline.py`를 통하는 것인지
적혀 있지 않습니다. 이 선택이 수정 범위를 바꿉니다.

| 진입점 | 필요한 수정 |
| --- | --- |
| `audit_mimic_quality.py` + `run_mimic_image_batch.py` 직접 호출 | `audit_mimic_quality.py`의 허용오차 인자만 |
| `run_screened_mimic_pipeline.py` 경유 | 위에 더해 `:29`, `:182`, `:203`, `:222-223`, `:297` 네 단정의 인자화 |

계획의 고칠 파일 표는 후자를 전제로 두 파일을 모두 싣고 있습니다. 안전한 쪽이지만,
전자로 간다면 `run_screened_mimic_pipeline.py` 수정이 불필요해져 작업량과 회귀 위험이 줄어듭니다.
어느 쪽인지 764행에 한 줄로 적으십시오.

#### F7 상세

528-529행이 "E 에피소드의 프레임 수와 내용 해시가 세 데이터셋에서 일치하는지 확인한다"고 규정한 것은 좋습니다.
다만 arm마다 **자기 학습 집합 통계로 정규화**하므로(2.2.1 채택 근거 4항이 그렇게 적고 있습니다),
같은 E 프레임이라도 프로브에 들어가는 정규화 값은 arm마다 다릅니다.

이것은 의도된 설계이고 판정은 후처리에서 rad로 역정규화한 뒤 하므로 문제가 아닙니다.
다만 세 모델의 E 지표를 비교할 때 정규화 통계 차이가 숨은 변수로 남으므로,
**arm별 `policy_preprocessor` 정규화 safetensors의 sha256을 근거 JSON에 남기십시오.**
그래야 나중에 "같은 E인데 왜 다른가"를 감사할 수 있습니다.
